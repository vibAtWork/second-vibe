# Decisions

- **Original game, same mechanics.** The game is called "Ricochet Arena" and has its own art, sounds and procedural mazes. Only the mechanics (speeds, turn rate, sub-steps, bounce rule, timings, key bindings) match the supplied SWF.
- **Maze generator:** a randomized DFS spanning tree, then 30% of the remaining interior walls are removed. Every cell is reachable and there are loops. The original's generator could leave unreachable pockets; that wasn't worth copying.
- **Tank size 0.32 × 0.40 cells** (approximated). The muzzle is a collision point at 4.5/16 cells (the original's bullet spawn distance), so bullets never spawn inside walls.
- **Fire taps are latched** until the next 25 Hz tick, so a key tap shorter than 40 ms still fires. The original polled the key once per frame and could miss very short taps.
- **Approach 1 netcode:** authoritative server, one queued input per tick, client prediction for your own tank only, 90 ms interpolation for everything else. Input frames are re-sent 4× for loss tolerance.
- **Approach 2 (P2P):** the first browser to claim the peer id `ricochet-arena-v1-<room>` hosts. A random back-off picks the new host when one leaves. Close events from WebRTC aren't reliable, so a 2.5 s snapshot timeout (guest side) and a 6 s silence timeout (host side) detect drops. PeerJS is vendored so the page doesn't depend on a CDN.
- **Bullet limit = 1**, from the original's default settings block (`settingsMaxBullets = 1`). My earlier value of 5 was a wrong assumption.
- **Crate pickup** uses the original rule (a crate corner inside the tank), plus "tank centre over the crate". The tank size is approximated, and without the extra rule a tank parked squarely on a crate turned 45° would miss it.
- **Frag shards** follow the original's code path literally: on touching a wall a shard stops for the rest of that frame instead of bouncing, so it creeps slowly through walls while fading.
- **Gatling rounds** start moving on the frame they're fired, like other projectiles.
- **Frag shards pass through walls** (changed on the owner's feedback about the original). Earlier I read the code as making them stall at walls.
- **Missile smoke**: grey before lock-on, then ~50% of puffs use the target's colour. The snapshot carries the target id for this.
- **Anti-cheat (server):** the server already runs the game. Hardening: strict validation, per-seat control scheme lock, one frame per tick, rate limit and kick, name sanitising.
- **Anti-cheat (P2P):** I chose replay auditing over lockstep or rollback. The host stays authoritative (smooth play) and guests verify it after the fact with per-tick hashes. This needed bit-exact trig (`dmath.js`) because `Math.sin` etc. may differ across engines. Join nonces go into the round seed so the host can't choose mazes alone.
- **Shared code instead of copies:** the P2P folder no longer copies shared code. It reuses the server project's files through its dev server and a `build.mjs` that produces `dist/` for static hosting. The Docker build stays self-contained because it only needs the server folder.
- **Refactor:** a protocol field list replaces positional indexing; one `busy` flag replaces four weapon flags; a `PROJECTILES` table plus `spawn()`; the client is split into game-client/render/audio/transport. JS went from 3,042 to 1,926 lines across both projects, with anti-cheat added.
- **Server-side behavioural anti-cheat** (`anticheat.js`): shots are judged by replaying them in the deterministic sim (ricochet kills + reaction ticks). Mouse snaps are measured as pointer jump distance, not aim angle: angle-based detection falsely flagged a smooth mouse player when the pointer passed near their own tank or they respawned. Defaults are conservative and validated against 12 simulated human games with zero flags. Kicks need two independent strong signals (or one overwhelming one). Kicked addresses get a 10-minute ban. `ANTICHEAT=kick|flag|off`; `/admin/reports` only with `ADMIN_TOKEN`.
- **Lag switch**: a seat with no input for 8 ticks idles instead of repeating its last input. The P2P auditor accepts that idle frame.
- **Anti-cheat must not hurt honest play** (owner's requirement), so:
  - the detector is isolated with try/catch (it disables itself, never the game) and has a 3 ms budget with tick skipping; measured at about 0.05 ms per tick
  - address bans are off by default (shared home IPs)
  - starvation idle moved from 8 to 38 ticks (1.5 s), so Wi-Fi hiccups don't stutter
  - mouse-snap kick limit raised to 15 per minute
  - a P2P host is called stale only if snapshots keep coming without audit logs (a frozen tab is lag, not cheating)
  - the flaky network test was fixed to send in step with server ticks (it was timer jitter, not a game bug)
- **Reports go to the players** (the owner runs the server unattended). Flags are broadcast with every snapshot and shown on the scoreboard and in a reports panel. A strict majority of the other players can vote out a flagged player; non-flagged players can't be voted on, which prevents ganging up.
- **Anti-cheat UI stays out of the playfield** (owner's request): no canvas banners. Flags, removals and P2P cheat detection appear only in the panel below the game and as the ⚠ on the scoreboard. Messages drop off after a minute.
- **Go rewrite dropped** at the owner's request; the backend stays JavaScript so the browser and server share one simulation. Paused Go WIP files removed.
- **Latest LTS, fewer dependencies:** Node 26.13.1 LTS on Alpine 3.24. Replaced the `ws` package with a ~90-line built-in WebSocket server (`ws.js`), so the server has zero npm dependencies. The image is Alpine plus the node binary and its 3 runtime libraries (no npm, yarn or corepack): 151 MB unpacked, 53 MB download (was 172 MB / 59 MB). With no RUN steps, multi-arch builds need no QEMU. GitHub Actions bumped to the latest majors (checkout/setup-node v7, buildx/login v4, build-push v7).
- **Graveyard Shift instead of a recreation:** the second SWF is a well-known game, so I built an original game in its genre with its mechanics (weapon set on keys 1-0 unlocked by score, placeables, multiplier, local 2-player). It has a new name, art, enemies' look, sounds and generated maps. The SWF's ActionScript is deliberately obfuscated (junk opcodes, scrambled jumps), so I designed the numbers myself instead of extracting them; only readable strings (weapon names/keys, upgrade names) informed the design.
- **Graveyard Shift reuses the tank game's design** (authoritative server, prediction, interpolation, zero-dependency `ws.js`, slim image) but not its behavioural anti-cheat: it's co-op, so validation, rate limits and server authority are enough.
- **Graveyard Shift rules now come from the reverse-engineered SWF logic** (RE-NOTES.md), replacing my earlier invented numbers; art, name and maps stay original. Gaps the code didn't settle (attack cadences, explosion radius, pellet counts, deathmatch frag limit) are documented choices.
- **Placing fix:** solid objects go on the first tile ahead that doesn't overlap the placer, so placement no longer fails depending on where you stand within your tile.
- **Graveyard Shift deathmatch stays at level 1:** zombies keep coming at level-1 strength for the whole match, since levels mean nothing when the goal is frags. Playtest bots rarely reach 10 frags only because they blow themselves up with ×200 explosives (104 of 109 downs); the frag rules themselves were checked.
- **Input queue overflow keeps one-shot inputs:** when a client gets more than 4 frames ahead, the server still drops the oldest frames (anti-speedhack), but moves their weapon switch and fire bit onto the next frame, so a press is never silently lost.
- **Graveyard Shift input buffer trimming:** each second, if a seat's queue never dropped below 2 frames at tick time, the oldest frame is dropped (its weapon switch and fire bit move to the next frame). Own movement may correct by up to one step (2 px), which the client's correction smoothing hides. That's cheaper than up to 60 ms of extra input delay.
- **Adaptive interpolation:** delay = snapshot interval (40 ms) + worst recent lateness + 6 ms, clamped to 45–200 ms. It grows fast after a spike and shrinks slowly. I kept snapshots at 25 Hz instead of 50 Hz to avoid doubling upload bandwidth for people hosting at home.
- **Own-shot prediction scope:** only weapons that always fire (guns, shotgun, railgun, rocket, grenade) play locally. Placing can fail, so it waits for the server. Death can't be predicted, so for one round trip after dying the browser may play a shot or two that never happened (tests: about 1-2 per death); a shot the browser didn't predict still plays from the server event, just late. Tracers (where the shot hit) still come from the server, which decides hits.
- **50 updates/s by default:** the owner asked for it. It costs 30-60 KB/s of upload per player (about 2 Mbit/s for a full 4-player game), so `SNAPSHOT_HZ=25` restores the old rate. The browser measures the update interval itself, so either setting needs no client change.
- **Quick fire re-press:** a release and re-press of fire inside one 20 ms input frame is now sent as release-then-press over two frames (20 ms later), rather than being merged into one long hold.
- **Short Fuse instead of a recreation:** the third SWF is a well-known grid bomber. Short Fuse keeps its recovered mechanics and numbers exactly, but the name, art, sounds and arena layouts are new (classic uses the original's crate generator; the fire-line and teleporter layouts are different shapes). Started on the original's 24 fps tick and 30-unit cells so the ported movement stays exact.
- **Original bugs fixed, not reproduced:** a carried bomb follows its carrier (the original followed its layer); a thrown bomb's slot goes back to its layer (the original credited the thrower, so the layer lost a bomb for good); fire-line tiles can hit once per burn, not once per round; chain reactions always go off on the next tick; sudden-death walls crush bombs and pickups under them. All are listed in projects/short-fuse/RE-NOTES.md.
- **Short Fuse heats end when every human is out** (ported from the original's round check), so players don't watch bots stall to the time limit; bots tied on lives make it a draw.
- **Short Fuse late inputs: wait, don't guess.** Repeating the last input while a frame is late (then compensating) still desynced under heavy jitter. Standing still for that tick and applying the frame on arrival never disagrees with the player's own screen; others can't see a one-tick pause through interpolation. Trimming is restricted to idle frames for the same reason.
- **Fair flames online:** a flame arm still gets used up by its first hit (original rule) but hits every player in it on that tick, instead of favouring the lowest player number.
- **Original art/music not copied or imitated.** The owner said they made the original; I can't verify that, and the original is a published game. So I built a skin loader instead: they can supply their own asset files via `SKIN_DIR` at run time. Short Fuse's built-in art and an original soundtrack stay in the repo; mechanics stay exactly as recovered.
- **Catch-up instead of trimming:** dropping (even idle) frames can't keep up with players who never stop moving. Applying two frames in one tick keeps prediction exact; a frame budget of real time + 3% stops this becoming a speed hack.
